# Media Relay Bridge — 작업 일지 (2026-05-08)

> 8K HEIC 단일/다중 변환 안정화. 시스템 HEIF 디코더가 거부하는 케이스를
> 자체 ISO BMFF 파서 + MediaCodec 직접 구동으로 우회.

---

## 1. 배경 / 문제

- 안드로이드 시스템 `ImageDecoder` (AOSP `HeifDecoderImpl`)가
  특정 8K 단일-타일 `hvc1` HEIC를 거부하는 사례 발생.
- 갤럭시 등에서 만든 HEIC가 카카오톡 등으로 전달될 때 `image/jpeg`로
  MIME이 위장되는 케이스도 존재 → 파일 헤더(ftyp brand)까지 봐야 분류 가능.
- 다중 공유 시(예: 25장) 한 장이 실패하면 형제 코루틴까지 같이 무너지는
  구조적 문제.
- 8K ARGB_8888 비트맵 ≈ 132MB → 동시 다중 디코드는 OOM 위험.

구버전 APK가 남아있던 상태**. 새 APK 설치 후에는 재현되지 않음.

## 3. 핵심 아키텍처 (4단계 폴백)

`ImageConverter.decode()`가 다음 순서로 시도:

```
1. ImageDecoder (default allocator)
   ↓ 실패
2. ImageDecoder (ALLOCATOR_SOFTWARE)
   ↓ 실패
3. HeifParser → HevcStillDecoder  ← 오늘 추가
   ↓ 실패
4. BitmapFactory (plain JPEG/PNG 보호용)
```

3단계가 핵심. 시스템이 "이 HEIC는 디코드 못해"라고 거절해도, 우리가
직접 ISO BMFF에서 `hvc1` 페이로드와 `hvcC`를 끄집어내 MediaCodec에 먹임.

## 5. 구현 요점

### 5-1. ISO BMFF 파싱 (`HeifParser.kt`)

읽는 박스만 추림:

- `ftyp` — 검증
- `meta` (FullBox)
  - `pitm` — primary item id
  - `iinf` / `infe` — itemId ↔ itemType (`hvc1`, `grid`, …)
  - `iloc` — itemId의 파일 내 offset/length (v0/1/2 모두 지원, 가변 폭 정수)
  - `iprp`
    - `ipco` — 프로퍼티 배열 (인덱스 1-based)
      - `ispe` (width/height)
      - `hvcC` (HEVCDecoderConfigurationRecord)
    - `ipma` — itemId → property index 배열
  - `iref` (FullBox)
    - `dimg` — grid → tile id 매핑

출력 sealed type:

```kotlin
sealed interface PrimaryItem {
    data class HevcStill(width, height, hvcC, payload)
    data class HevcGrid(outputW/H, rows, cols, tileW/H, hvcC, tilePayloads)  // 파싱만 됨, 디코드 미구현
    data class Unsupported(reason)
}
```

### 5-2. HEVC 비트스트림 변환 (`HevcStillDecoder.kt`)

HEIF에 들어있는 HEVC는 **length-prefixed NAL** 형식이라 그대로 MediaCodec에
넣을 수 없음. 두 가지 변환 필요:

1. **CSD-0 만들기**: `hvcC`의 `numOfArrays` 루프를 돌며 VPS/SPS/PPS NAL을
   추출해 Annex-B (`00 00 00 01` start code)로 이어붙임.
2. **페이로드 변환**: `hvcC[21] & 0x3 + 1` = lengthSize. 페이로드를 그
   길이만큼 잘라가며 Annex-B로 prefix 교체.

### 5-3. 디코더 선택

`MediaCodecList(REGULAR_CODECS)` 순회 → `video/hevc` 지원 + `isSizeSupported(w,h)` 통과
→ HW 우선, SW 후순위. 8K가 fit하는 디코더만 후보로 남김.

### 5-4. YUV → Bitmap

ImageReader를 `YUV_420_888`로 받고 BT.601 limited-range 정수 매트릭스로
ARGB_8888 비트맵 생성. (HEIC color info 무시 — 안전한 기본값.)
NV12 / I420 모두 `pixelStride`/`rowStride` 사용해 일관 처리.

### 5-5. 실패 격리 (`ShareReceiverActivity.kt`)

```kotlin
val result = try {
    when (detection.kind) {
        IMAGE -> imageConv.convert(uri)
        VIDEO -> videoConv.convert(uri) { }
        UNKNOWN -> Skipped(...)
    }
} catch (t: Throwable) {
    ConversionResult.Failed(...)
}
```

각 async 코루틴이 자기 예외를 잡아 sibling을 안 죽임. coroutineScope의
"한 자식이 throw하면 모두 cancel" 동작 회피.

### 5-6. 동시성

```kotlin
val cpus = Runtime.getRuntime().availableProcessors()
val concurrency = inputs.size.coerceAtMost(maxOf(1, minOf(2, cpus / 2)))
```

8K HEVC 디코더 인스턴스는 무거움. HW 디코더 풀 자체가 작음. 동시 2개면
충분히 빠르고 OOM 위험도 낮음.
